# ADR-001: Domain-Driven Design with Hexagonal Architecture

**Status:** Accepted  
**Date:** 2026-08-06  
**Deciders:** Architecture Team

## Context

The Orbis platform manages complex business domains (identity, inventory, support, organization, expense, etc.) with rich business logic, invariants, and cross-domain interactions. The team needed an architecture that:

- Separates domain logic from infrastructure concerns
- Allows independent testing of business rules
- Supports multiple delivery mechanisms (API, Web, CLI)
- Enables team autonomy across bounded contexts
- Handles complex validation and state transitions

## Decision

Adopt **Domain-Driven Design (DDD)** with **Hexagonal Architecture** (Ports and Adapters) as the foundational architectural style.

### Key Principles Applied

1. **Domain Layer Purity:** Domain entities, value objects, and events contain zero framework dependencies
2. **Port Interfaces:** Repositories, services, and notifiers defined as interfaces in Domain
3. **Adapter Implementations:** Doctrine repositories, Symfony mailers, external APIs implemented in Infrastructure
4. **Application Layer:** Orchestrates use cases via Commands and Queries (CQRS)
5. **Bounded Contexts:** Each major domain area is a separate BC with explicit integration contracts

## Consequences

### Positive
- Business logic is isolated and testable without framework bootstrapping
- Multiple presentation layers (API, Web, CLI) share the same application services
- Team can work on different BCs with minimal coordination
- Infrastructure changes (DB, messaging) don't affect domain logic

### Negative
- Initial boilerplate for ports and adapters
- Learning curve for developers unfamiliar with DDD/Hexagonal
- More files/layers for simple operations

### Neutral
- Requires discipline to maintain domain purity
- Integration tests needed to verify adapter implementations
