# ADR-004: Custom DBAL Types for Domain Primitives

**Status:** Accepted  
**Date:** 2026-08-06  
**Deciders:** Architecture Team

## Context

PHP's type system lacks strong typing for domain concepts. A `user_id` string looks identical to a `product_id` string at the database level, leading to potential bugs when values are mixed. Additionally, PHP enums (PHP 8.1+) need custom database mapping for Doctrine persistence.

## Decision

Create custom Doctrine DBAL types for every domain primitive that requires type safety at the database layer.

### Type Mapping

| PHP Type | DBAL Type | Database Column |
|----------|-----------|-----------------|
| `UserIdValueObject` | `user_id` | VARCHAR(26) |
| `UsernameValueObject` | `username` | VARCHAR(20) |
| `HashedPasswordValueObject` | `hashed_password` | VARCHAR(255) |
| `RoleIdValueObject` | `role_id` | VARCHAR(26) |
| `RoleNameValueObject` | `role_name` | VARCHAR(50) |
| `RoleStatus` (enum) | `role_status` | VARCHAR(20) |
| `UserStatus` (enum) | `user_status` | VARCHAR(20) |
| `PermissionIdValueObject` | `permission_id` | VARCHAR(26) |
| `PermissionKeyValueObject` | `permission_key` | VARCHAR(100) |
| `TokenHashValueObject` | `token_hash` | VARCHAR(64) |
| `AuthLogIdValueObject` | `auth_log_id` | VARCHAR(26) |
| `AuthEvent` (enum) | `auth_event` | VARCHAR(30) |

### Implementation Pattern

```php
// src/app/Identity/Infrastructure/Doctrine/Types/UserIdType.php
class UserIdType extends Type
{
    public function getName(): string { return 'user_id'; }
    public function getSQLDeclaration(array $column, AbstractPlatform $platform): string
    {
        return $platform->getVarcharTypeDeclarationSQL(['length' => 26]);
    }
    public function convertToPHPValue(mixed $value, AbstractPlatform $platform): UserIdValueObject
    {
        return new UserIdValueObject($value);
    }
    public function convertToDatabaseValue(mixed $value, AbstractPlatform $platform): string
    {
        if ($value instanceof UserIdValueObject) {
            return $value->value();
        }
        return (string) $value;
    }
}
```

## Consequences

### Positive
- Type safety at the database boundary
- Self-documenting schema (column types are meaningful)
- Prevents accidental mixing of ID types
- PHP 8.4 enum compatibility via custom types

### Negative
- Requires registering each type in Doctrine configuration
- Additional classes to maintain
- Slight overhead for simple string fields

### Neutral
- Consistent pattern across all BCs
- Makes migrations and schema inspection more readable
