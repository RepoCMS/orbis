# ADR-006: Symfony Messenger for Event Bus

**Status:** Accepted  
**Date:** 2026-08-06  
**Deciders:** Architecture Team

## Context

The system requires reliable communication between BCs and internal components:
- Domain events need to be dispatched and handled
- Cross-BC integration needs asynchronous processing capability
- Command handlers need to be dispatched through a bus
- Future needs may include message queuing for long-running operations

## Decision

Use **Symfony Messenger** as the message bus implementation.

### Configuration

```yaml
# config/packages/messenger.yaml
framework:
    messenger:
        failure_transport: failed
        transports:
            async:
                dsn: '%env(MESSENGER_TRANSPORT_DSN)%'
                retry_strategy:
                    max_retries: 3
                    delay: 1000
        routing:
            'App\Shared\Domain\Event\*': async
```

### Message Types

| Type | Transport | Purpose |
|------|-----------|---------|
| Command | Sync | Immediate execution (write operations) |
| Query | Sync | Immediate execution (read operations) |
| Domain Event | Sync (current), Async (future) | Internal state changes |
| Integration Event | Async | Cross-BC communication |

### Handler Pattern

```php
#[AsMessageHandler]
final readonly class RecordFailedLoginHandler implements MessageHandlerInterface
{
    public function __invoke(RecordFailedLoginCommand $command): void
    {
        // Handler logic
    }
}
```

## Consequences

### Positive
- Standard Symfony component with excellent tooling
- Async transport support for future scalability
- Built-in retry and failure handling
- Consistent dispatch pattern across the codebase

### Negative
- Additional configuration complexity
- Async transport requires message broker (RabbitMQ, Redis, etc.)
- Debugging async flows requires additional tooling

### Neutral
- Synchronous by default for simplicity
- Can evolve to async without changing handler signatures
