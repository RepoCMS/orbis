# ADR-002: CQRS Pattern for Commands and Queries

**Status:** Accepted  
**Date:** 2026-08-06  
**Deciders:** Architecture Team

## Context

The system has distinct read and write concerns:
- Writes involve complex validation, business rules, and state transitions
- Reads require optimized queries, denormalized views, and different data shapes
- Mixing both in single models leads to complexity and performance issues

## Decision

Adopt **Command Query Responsibility Segregation (CQRS)** at the Application Layer:

- **Commands** represent intent to change state (write operations)
- **Queries** represent data retrieval needs (read operations)
- Each has dedicated handlers, DTOs, and validation

### Implementation Details

```
Application/
├── Command/
│   ├── {Action}{Resource}Command.php      # Input DTO
│   └── {Action}{Resource}Handler.php      # Handler (invokable)
├── Query/
│   ├── {Find|List}{Resource}Query.php     # Input DTO
│   ├── {Find|List}{Resource}Handler.php   # Handler (invokable)
│   └── Response/
│       └── {Resource}Response.php         # Output DTO
```

### Rules

1. Every Command/Query must have a real caller (controller, console, event subscriber)
2. Handlers are single-action invokable classes (`__invoke()`)
3. Commands return void or domain IDs; Queries return Response DTOs
4. Validation happens in Command/Query constructors and Handlers

## Consequences

### Positive
- Optimized read models for dashboards, lists, reports
- Write models enforce invariants without read concerns
- Clear separation enables different persistence strategies
- Easier testing - commands and queries tested independently

### Negative
- More classes for simple CRUD operations
- Eventual consistency between read/write models (mitigated by synchronous handlers)
- Potential duplication of validation logic

### Neutral
- Requires convention adherence (enforced by code review)
- Works well with Symfony Messenger for command bus
