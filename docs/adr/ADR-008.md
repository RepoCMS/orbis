# ADR-008: Soft Delete Pattern

**Status:** Accepted  
**Date:** 2026-08-06  
**Deciders:** Architecture Team

## Context

The system requires the ability to "delete" entities without actually removing them from the database, for:
- Audit trail compliance
- Accidental deletion recovery
- Data integrity (foreign key constraints)
- Regulatory requirements

## Decision

Implement soft delete using a `deleted_at` timestamp column on all entities.

### Implementation Pattern

```php
// In every aggregate root entity
abstract class SoftDeleteEntity
{
    protected ?DateTimeImmutable $deletedAt = null;
    
    public function softDelete(): void
    {
        $this->deletedAt = new DateTimeImmutable();
    }
    
    public function isDeleted(): bool
    {
        return $this->deletedAt !== null;
    }
}
```

### Repository Filtering

All repository queries automatically filter out soft-deleted records:

```php
// In every Doctrine repository
protected function applySoftDeleteFilter(QueryBuilder $qb): void
{
    $qb->andWhere('e.deletedAt IS NULL');
}
```

### Naming Convention

- Column: `deleted_at` (snake_case)
- Property: `deletedAt` (camelCase)
- Method: `softDelete()` (not `delete()`)
- Scope: All entities in all BCs

## Consequences

### Positive
- Data is never permanently lost
- Audit compliance is maintained
- Foreign key integrity is preserved
- Recovery from accidental deletion is trivial

### Negative
- All queries must filter `deleted_at IS NULL`
- Storage grows indefinitely (mitigated by archival strategy)
- Unique constraints must account for soft-deleted records

### Neutral
- Consistent pattern across all BCs
- Requires discipline to never bypass soft delete
