# ADR-007: Shared Kernel for Cross-BC Integration

**Status:** Accepted  
**Date:** 2026-08-06  
**Deciders:** Architecture Team

## Context

Bounded Contexts need to share certain concepts without tight coupling:
- User identity references across BCs (Organization links to User, Client links to User)
- Common value objects (ULID-based IDs)
- Cross-BC query interfaces (e.g., resolving email across Org and Client)
- Shared event patterns

## Decision

Implement a **Shared Kernel** module at `src/app/Shared/` that contains:

### Shared Kernel Contents

| Component | Location | Purpose |
|-----------|----------|---------|
| Value Objects | `Shared/Domain/ValueObjects/` | ULID, Email, Phone, etc. |
| Interfaces | `Shared/Domain/Contracts/` | Cross-BC repository interfaces |
| Events | `Shared/Domain/Event/` | Shared domain events |
| Services | `Shared/Domain/Service/` | Cross-BC service interfaces |
| Exceptions | `Shared/Exceptions/` | Shared exception types |
| DBAL Types | `Shared/Infrastructure/Doctrine/Types/` | Common DBAL types |
| Import/Export | `Shared/Infrastructure/Import/`, `Shared/Infrastructure/Export/` | Shared import/export infrastructure |

### Integration Rules

1. **No BC may depend on another BC's internal implementation**
2. **Shared Kernel contains only interfaces and contracts**
3. **Each BC implements Shared Kernel interfaces in its own Infrastructure**
4. **Cross-BC references use IDs only** (never direct entity references)
5. **Shared Kernel changes require approval from all BC owners**

### Cross-BC Resolution Pattern

```php
// Shared Kernel interface
interface UserEmailResolverInterface
{
    public function resolveEmail(UserIdValueObject $userId): ?string;
}

// Identity BC implementation
class CrossBcUserEmailResolver implements UserEmailResolverInterface
{
    public function resolveEmail(UserIdValueObject $userId): ?string
    {
        // Check Organization BC, then Client BC
    }
}
```

## Consequences

### Positive
- Clean separation of BC internals
- Shared primitives without coupling
- Each BC owns its implementation of shared contracts
- Easy to evolve shared contracts independently

### Negative
- Shared Kernel can become a bottleneck if not governed
- Requires discipline to keep it minimal
- Cross-BC queries can become complex

### Neutral
- The Shared Kernel is the "seams" between BCs
- Well-defined boundaries enable team autonomy
